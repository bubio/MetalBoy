# MetalBoy Constitution

## Core Principles

### I. Objective-C 一元化
MetalBoy プロジェクトのすべてのコード（エミュレーション本体、CLI ツール、
デバッガ、テストヘルパー、補助ツールを含む）は Objective-C で MUST 記述する。
最新の Objective-C 記法（モダンなプロパティ宣言、ARC、`instancetype`、
blocks、Generics などの現行の慣用的構文）を MUST 採用する。他言語での
実装は、ターゲット環境が Objective-C を提供しない例外的な場合に限り許可し、
その理由を PR 内で明示しなければならない（MUST）。

**根拠**: 単一言語化により型安全性・ツールチェーン統一・コード再利用を
保証し、メンテナンスコストを下げるため。macOS 26+ を対象とし、最新の
Objective-C の機能とランタイムを優先利用する。

### II. ライブラリー・ファースト
すべての機能は、自己完結し単体テスト可能なモジュールとして MUST 開始する。
各モジュールは明確な公開 API と目的を持つこと（MUST）。コードは MUST 次の
層に分離し、上位層から下位層への依存のみを許す（下位層が上位層を知っては
ならない = MUST NOT）。

- **エミュレーションコア層**: CPU / PPU / APU / メモリ / カートリッジ等。
  UI・OS 固有の依存を持たない純粋なコアとする
- **機能層**: セーブデータ管理、キー入力抽象化、オプション解釈などコアと
  UI/ホストをつなぐ橋渡し。OS 依存は最小限に限定する
- **UI 層**: 画面表示・音声出力・ウィンドウ管理などホスト環境固有の実装。

組織的整理だけを目的としたモジュールは作成してはならない（MUST NOT）。
ホストアプリ・CLI はライブラリの薄いラッパーとして位置づける。

**根拠**: コアと UI を分離することで、テスト容易性と再利用性を確保し、
リグレッションを局所化するため。層の境目の明確化は原則 VI
（ポータビリティ）の前提条件でもある。

### III. 仕様準拠と正確性
Game Boy（DMG）ハードウェアの挙動は、公開された技術資料（Pan Docs、GBATEK 等）
に準拠し MUST 実装する。現在のスコープは DMG（初代 Game Boy）であり、
CGB 専用機能は対応範囲外とする（機能仕様で確定済み）。仕様と実装の食い違いがある
場合、出典を添えて仕様側の記述を
優先する（MUST）。性能最適化は正確性を妥協しない範囲でのみ行うこと（MUST）。
意図的な仕様逸脱（バグエミュレーション等）は constitution 上の例外的合意として
ドキュメント化しない限り行ってはならない（MUST NOT）。

**根拠**: エミュレータの価値は正確性にあり、恣意的な判断による挙動の漂白を防ぐため。

### IV. テスト・ファースト（非交渉可能）
TDD は必須とする（MUST）：（1）テストを書く →（2）期待する挙動を合意 →
（3）テストが失敗することを確認 →（4）実装する。Red-Green-Refactor サイクルを
厳格に守ること（MUST）。ハードウェア再現検証には公開テスト ROM
（blargg/mooneye 等のスイート）を Objective-C 製のテストランナーで実行できることが
必須である（MUST）。実装なしに済む機能のテストは禁止されない（SHOULD で奨励）。

**根拠**: エミュレータは多数の微小な正確性条件の積み重ねであり、先行的テストなしでは
バグの所在が特定不能になるため。テスト ROM ランナー自体も原則 I により
Objective-C で書くことで一貫性を保つ。

### V. シンプルさと可観測性
実装は可能な限りシンプルにし、YAGNI の原則に従うこと（MUST）。複雑性は明確な
利点と根拠を伴う場合に限り導入する（MUST）。tracing / ログ / デバッガ用の
CLI インターフェース（テキスト入出力：stdin/引数 → stdout、エラー → stderr、
機械可読 JSON と人間可読出力の両対応）を MUST 提供し、開発時の状態観測を可能に
すること（MUST）。未実装・未確定の挙動はログに必ず記録すること（MUST）。

**根拠**: テキスト I/O はデバッグに最も信頼性の高い手段であり、エミュレータ開発では
実行中の状態観測が生産性を直接左右するため。

### VI. ポータビリティ
エミュレーションコア層と機能層（原則 II）は、macOS 固有の API やグラフィックス
技術に直接依存してはならない（MUST NOT）。OS 固有の依存は UI 層に MUST 隔離
する。コア・機能層の公開インターフェースは、他 OS や SDL 等の移植可能な
描画・入力・音声の実装と接続できる設計とすること（SHOULD）。UI 固有の実装を
コアに逆流させてはならない（MUST NOT）。

**根拠**: 現在のホストは macOS 26+（UI 層）だが、コア資産をプラットフォーム
非依存に保つことで、他 OS や SDL ベースのフロントエンド追加を容易にし、
コアの書き直しコストを回避するため。

## 追加制約と技術要件

- **言語**: 実装言語は Objective-C（最新のモダン記法、ARC 必須）とする
  （MUST）。補助ツール・スクリプトも Objective-C 製を基本とする（MUST）。
  ビルド・パッケージ管理は Xcode プロジェクトを基本とする（SHOULD）。
- **対象プラットフォーム**: macOS 26.0 以降を MUST 対象とする。これより古い
  macOS の互換性維持は要求としない。他 OS のサポートはコア・機能層の
  ポータビリティ（原則 VI）を通じて将来追加できる（MAY）。
- **命名**: リポジトリ/フォルダ名は `SwiftGB`、アプリケーション名は
  `MetalBoy` とする（MUST）。コード内のターゲット・モジュール名は
  MetalBoy 由来の命名を基本とする（SHOULD）。歴史的経緯でフォルダ名だけが
  SwiftGB に留まる点は文書化済みの例外とする。
- **プロジェクト構成**: 層分離（エミュレーションコア / 機能 / UI）を
  ターゲット/モジュール分割として MUST 反映する（原則 II 参照）。
- **プロジェクトの基本言語（自然言語）**: ドキュメント、ADR、テスト記述、
  コミットメッセージ、レビューコメントは日本語を基本とする（MUST）。
  ソースコード内識別子は英語とする（SHOULD）。公開仕様を引用する場合は出典の
  原文言語（英語等）をそのまま保持できる（MAY）。
- **互換性**: ライブラリの公開 API 変更はセマンティックバージョニングに従う
  （MUST。MAJOR.MINOR.PATCH）。
- **ネットワーク**: 特段の理由がなければネットワーク依存を追加しては
  ならない（MUST NOT）。

## 開発ワークフローと品質ゲート

- **Spec Kit フロー**: 機能は `/speckit.specify` → `/speckit.clarify` →
  `/speckit.plan` → `/speckit.tasks` → `/speckit.implement` の順で MUST 進める。
- **コードレビュー**: すべての PR はレビュー必須とし、Constitution への適合性
  （I〜VI、技術要件）を確認すること（MUST）。
- **テストゲート**: コミット前はすべてのユニットテストがパスしていること（MUST）。
  リリース/マージ前にはテスト ROM スイート（IV）の実行を必須とする（MUST）。
- **複雑性の正当化**: 直接的に課題を解決しない抽象化・オプションパラメータ・
  将来機能の先延ばし実装は禁止である（MUST NOT）。
- **ドキュメント**: 機能追加・仕様逸脱・設計判断の都度、`docs/` 配下に記録する
  こと（SHOULD）。

## Governance

- 本 Constitution は MetalBoy プロジェクトにおける他のすべての開発実践・慣行に
  優先する（MUST）。コミット・レビュー時には適合性を確認し、非準合を発見した
  場合は修正または憲法改正提案を選択すること（MUST）。
- **改正手順**: 改正は本文書の直接編集によって行う。改正には変更理由・影響範囲・
  移行計画を Sync Impact Report に記録すること（MUST）。
- **バージョニング**: セマンティックバージョニング
  （MAJOR: 原則の削除・非互換の再定義、MINOR: 原則・節の追加または実質的拡張、
  PATCH: 文言・非意味的修正）に従うこと（MUST）。
- **複雑性**: 追加の複雑性は正当化を必須とする（MUST）。
- 実行時の開発ガイダンスには本 Constitution に加えて `docs/` のガイダンスファイル
  を使用すること（SHOULD）。
